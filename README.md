# Longitudinal multiomic profiling and functional TCR screening in patient VHIO-136

This repository contains the analysis code used to identify and longitudinally characterize tumor-reactive T cells in patient VHIO-136. The study combines longitudinal bulk TCRβ sequencing of peripheral blood and a baseline tumor biopsy, flow-cytometry phenotyping of PBMCs, functional screening of a synthetic library of 1,001 candidate TCRs, and single-cell RNA/TCR sequencing.

## Workflow

The analysis is organized into four main steps:

1. **Longitudinal TCR repertoire and phenotypic profiling** (section 4). Track TCRβ clonotypes across 12 blood timepoints and a baseline tumor biopsy, alongside changes in T-cell phenotypes by flow cytometry. These data, together with single-cell TCR sequencing (rootpath, pre and post2), guided the selection of 1,001 TCRs for functional screening, including those from the PD-1<sup>hi</sup> fraction and abundant, expanding, or tumor-shared clonotypes. Selection criteria and screening results are annotated in `data/aux/tcr-library/tcr_library_annotated.txt`.
2. **TCR library screen** (section 5). The synthetic TCR library is expressed in healthy-donor T cells, which are challenged with target cells and sorted by 4-1BB expression. Candidate reactive TCRs are identified by enrichment in the 4-1BB+ fraction compared with 4-1BB− or unsorted T cells: FASTQ → construct counts → edgeR → volcano plots.
3. **Single-cell analysis** (section 6). Process and integrate longitudinal single-cell RNA/TCR sequencing data generated by RootPath (`rootpath`, pre and post2) and in-house (`vhio`, post1 and post6). By linking clonotypes to their functional screening results, we track tumor-reactive T cells over time and characterize their transcriptional states. We then identify timepoint-associated transcriptional features and test whether signatures derived from them can also distinguish tumor-reactive T cells in the independent Yossef et al. cohort.
4. **Bulk and single-cell integration** (section 7). Integrate longitudinal bulk TCRβ trajectories with single-cell phenotypes to visualize how tumor-reactive clonotypes expand, persist, or decline over time and how their transcriptional states change during treatment.

```
1. long-tracking   script-bulk-tcrb ─────────────────────┐
                   script-flow-phenotype                 ├─► 1,001 candidate TCRs (tcr_library.txt)
                   Cell Ranger rootpath (pre, post2) ────┘

2. tcr-library     run-hits.sh ─► script-hit-identification-TCL ─► script-volcano-plots-TCL
                   reactive TCR IDs ─► script-bulk-tcrb ─► tcr_library_annotated.txt ─┐
                                                                                      │
3. single-cell     m01-rootpath ─┐                                                    │
                   m01-vhio ─────┴─► m02 ◄────────────────────────────────────────────┘
                                     └─► m03 ─┬─► m04 ─► m05 ◄── m01-yossef
                                              │
4. integration                                └─► script-bulk-sc-phenotype
```

The candidate TCRs were selected from the longitudinal bulk TCRβ repertoire and the single-cell TCRs of the pre and post2 samples. Once screened, the reactive TCRs are recorded in `script-bulk-tcrb.Rmd` and reach the single-cell analysis through `tcr_library_annotated.txt`.

## 1. Recreate the environment

Requirements: Linux x86_64, [miniforge/conda](https://github.com/conda-forge/miniforge), git.

```bash
git clone git@github.com:eprieto012/vhio136.git
cd vhio136

# R 4.4.0 and system libraries
conda create -p ./envs/renv_vhio136 --file setup/env-lock/conda_renv_vhio136.explicit.txt

# Python environment for MAGIC
conda create -p ./envs/magic_env --file setup/env-lock/conda_magic_env.explicit.txt
./envs/magic_env/bin/pip install -r setup/env-lock/magic_env.pip.txt

# Alignment tools for the TCR library screen (fastp, cutadapt, seqkit, bowtie2, samtools)
conda create -p ./envs/tcrlib_hits --file setup/env-lock/conda_tcrlib_hits.explicit.txt

# Tell the launchers and setup.R where the environments are
export ENV_REPRO="$PWD/envs/renv_vhio136"
export MAGIC_PYTHON="$PWD/envs/magic_env/bin/python"
export ENV_HITS="$PWD/envs/tcrlib_hits"

# Start R inside the renv project and install the exact package versions
./scripts/interactive-R.sh
```

```r
renv::restore()   # installs the 348 packages recorded in renv.lock
renv::status()    # should report: "No issues found"
```

`interactive-R.sh` puts the conda R first on `PATH`, unsets `R_LIBS*` and starts R from `renv-vhio136/`, whose `.Rprofile` activates renv, so only the renv library is used. Always start R through it.

### Starting R

**Option A — VS Code (interactive, with plot viewer).** Requires the [R extension](https://marketplace.visualstudio.com/items?itemName=REditorSupport.r) (REditorSupport). Point the extension to the launcher in `.vscode/settings.json`:

```json
  "r.rterm.linux": "/absolute/path/to/vhio136/scripts/interactive-R.sh",
  "r.sessionWatcher": true,
  "r.plot.backend": "standard"

```

Then `Ctrl+Shift+P` → **R: Create R Terminal**. The first time, accept the notification asking to install the helper package `sess` (installed in the extension's own folder, not in the renv library). Run `.Rmd` chunks with `Ctrl+Enter`; plots appear in the R Plot panel.

**Option B — terminal (manual, or long batch runs).**

```bash
./scripts/interactive-R.sh   # interactive R session
tmux new -s vhio136          # recommended for long renders: survives disconnections
```

A session started this way is not connected to the VS Code plot viewer. To connect it, run `Ctrl+Shift+P` → **R: Attach External R Session (Copy command)** and paste the copied command into the R console.

`Rplots.pdf` is never written: `renv-vhio136/.Rprofile` sets a null PDF device in non-interactive sessions (`run-rmd.sh`) and in interactive sessions without a display (e.g. a compute node). Plots are shown only in the VS Code viewer, or saved explicitly by the scripts.

Check that the right environment is active in either case:

```r
renv::project()   # .../vhio136/renv-vhio136
.libPaths()[1]    # .../renv-vhio136/renv/library/...
```

The `.yml` files in `setup/env-lock/` are human-readable equivalents of the explicit specs, useful on non-Linux systems (versions approximate).

## 3. Running the R Markdown scripts

Every `.Rmd` (sections 4–7) is run from the project root with the SLURM launcher. Called directly (not through `sbatch`), `run-rmd.sh` creates `logs/` and `results/` if they do not exist and submits itself; any option before the `.Rmd` is passed to `sbatch`:

```bash
cd /path/to/vhio136
scripts/run-rmd.sh -J m01-rootpath scripts/single-cell/rmd/m01-data-load-rootpath.Rmd
scripts/run-rmd.sh -J m02-integration --mem=200gb scripts/single-cell/rmd/m02-data-integration.Rmd
```

- `logs/` must exist before `sbatch` is called (SLURM opens the log file before the job starts and does not create its directory). Calling `sbatch -J <name> scripts/run-rmd.sh <file>.Rmd` directly also works, but only if `logs/` already exists.
- Folders are only created when missing: `logs/` accumulates one `<name>_<jobid>.log` per job, and outputs in `results/` are overwritten when a script is re-run (files a script no longer produces are not removed).
- Resources default to the `#SBATCH` header of `run-rmd.sh` (25 CPUs, 100 GB). `m02` peaks at ~160 GB, so run it with `--mem=200gb`.
- A run that fails stops with `Execution halted` at the end of its log (and `sacct` reports `FAILED`); the single-cell scripts also end by printing `"Plots saved successfully."` when they finish.

To run a script interactively instead, start R with `interactive-R.sh` (it starts in `renv-vhio136/`, so project paths are `../setup`, `../results`, ...) and render it:

```r
rmarkdown::render("../scripts/single-cell/rmd/m01-data-load-rootpath.Rmd", knit_root_dir = getwd())
```

## 5. TCR library screen

The 1001-TCR library was transduced into T cells of two healthy donors (PDL5.9, PDL6.2), co-cultured with the antigen, and sorted by 4-1BB (activation marker). A reactive TCR is enriched in the 4-1BB+ fraction over the 4-1BB− one. Three conditions are screened: the **relevant** library (RIO136, the patient's own), the **irrelevant** library (RIO008, specificity control) and **B cells** as the positive control of the assay. Each donor was screened twice (2022 and 2024), giving 4 replicates per group for the relevant and irrelevant comparisons.

### Samples

Everything needed to run the screen from the original FASTQ files is in one table, `data/aux/tcr-library/tcr_library_screen_samples.tsv` (26 rows):

| Column            | Meaning                                                                                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `screen`        | `screen-1` (14 samples, sequenced 2022, two pools) or `screen-2` (12 samples, 2024)                                                               |
| `sample`        | FASTQ prefix: the reads are `<sample>_{1,2}.fastq.gz`                                                                                               |
| `fastq_dir`     | sequencing run folder in the original raw-data layout, relative to `RAW_DIR`                                                                        |
| `analysis_id`   | **the ID used in the analysis, which is not the FASTQ name**                                                                                    |
| `analysis_name` | `Screen<n>_<donor>_<library>_<fraction>`                                                                                                            |
| `orig_name`     | sample name as recorded in the lab                                                                                                                    |
| `included`      | `yes` for the 20 samples of the three volcano comparisons; `no` for the bulk and screen-2 B-cell samples, used only in the `*_bulk` comparisons |

**The renaming matters.** The sequencing IDs and the analysis IDs are different: `Screen1_TCR_1` is `PDL6.2_136TCL_41BBpos`, which the analysis calls `TCR_8`. The sequencing provider named the samples of both screens `TCR_<n>`, so the FASTQs were renamed with the screen as prefix (`Screen1_`, `Screen2_`) to keep `TCR_1` of screen-1 and `TCR_1` of screen-2, two different samples, apart. Ignoring the mapping compares the wrong groups without raising any error, so the alignment keeps the FASTQ names and the renaming is applied in R when the count matrix is built.

### 5.1 Alignment: FASTQ → counts

`scripts/tcr-library/hits/align_sample.py` processes one sample: fastp (16-nt UMI in read 2, deduplication, reads ≥ 100 nt, adapter trimming disabled), cutadapt (removal of the 5' vector sequences shared by every construct), removal of reads left empty in read 2 (seqkit), bowtie2 alignment to the library (`-N 0 --no-1mm-upfront`, default mode: one alignment per read) and counts per construct (samtools, read 1 only). Do not add `-a`: the codon variants of each TCR share most of their sequence, so most reads align to several constructs and `-a` would count each of them several times (about 5× the reads). `run-hits.sh` builds the bowtie2 index of `TCR_lib_RIO136_AAV.fasta` if missing and submits one SLURM array task per sample of the screen. It needs SLURM and the `tcrlib_hits` environment (section 1).

Place the FASTQs as `<RAW_DIR>/<screen>/<sample>_{1,2}.fastq.gz`, with `screen` and `sample` taken from the sample table (e.g. `screen-1/Screen1_TCR_1_1.fastq.gz`). The original layout of the sequencing runs, `<RAW_DIR>/<fastq_dir>/`, is also accepted; `RAW_DIR` defaults to the raw-data NAS where the screen was sequenced (`/mnt/petasan_immuno/raw_data/itag/VHIO/360RIO136`). The FASTQ files are read in place and never copied. Then, from the project root:

```bash
cd /path/to/vhio136
export RAW_DIR=/path/to/fastq ENV_HITS=/path/to/envs/tcrlib_hits
scripts/tcr-library/hits/run-hits.sh screen-1
scripts/tcr-library/hits/run-hits.sh screen-2
```

Each task runs in partition `long` with 16 CPUs, 32 GB and a 2-day limit; change them with `PARTITION`, `CPUS`, `MEM` and `WALLTIME` (e.g. `CPUS=100 MEM=256gb scripts/tcr-library/hits/run-hits.sh screen-1`). Memory grows with the number of CPUs. Alignment is the slow step (about 10 min per sample with 30 CPUs). The log of each task is `logs/hits_<screen>_<job>_<task>.log`; a task has finished correctly when it ends with `Counts written: ...`.

Outputs go to `results/tcr-library/<screen>/<sample>/`: `<sample>.counts.txt` (construct, read count), `<sample>.sam` (several GB), the fastp report and the log; `tmp/` keeps the intermediate FASTQs. **Only `<sample>.counts.txt` is used downstream**: the `.sam` and `tmp/` are kept and can be deleted by hand once the counts are checked.

The original counts (2022) were produced with fastp 0.23.2, cutadapt 4.0 and bowtie2 in default mode, which is what the `tcrlib_hits` environment and `align_sample.py` reproduce (bowtie2 2.4.5 and 2.5.5 give identical alignments). The result is not bit-identical, because fastp's UMI deduplication (`--dedup`) is not deterministic: two runs on the same FASTQ keep the same number of reads, but not always the same copy of each duplicate. A few reads therefore change construct, usually between codon variants of the same TCR. Tested on `Screen1_TCR_1` (two runs): 3,594,129–3,594,134 vs 3,594,136 reads, with 30–40 of 2,790 constructs differing by 1–3 reads.

### 5.2 Hit calling and volcano: counts → figures

```bash
scripts/run-rmd.sh -J tcl_hits scripts/tcr-library/rmd/script-hit-identification-TCL.Rmd
scripts/run-rmd.sh -J tcl_volcano scripts/tcr-library/rmd/script-volcano-plots-TCL.Rmd
```

`script-hit-identification-TCL.Rmd` joins the 26 count files into `results/tcr-library/counts/all.counts.txt` (renaming them to the analysis IDs) and runs edgeR on six comparisons: `relevant`, `irrelevant` and `positive` (4-1BB+ vs 4-1BB−), and `relevant_bulk`, `irrelevant_bulk` and `positive_bulk` (4-1BB+ vs the unsorted bulk). Each one keeps constructs above 10 CPM in at least one sample and samples with at least 100,000 reads, and tests the two groups with `exactTest` (BH-adjusted p-values). Results per comparison go to `results/tcr-library/edger/<comparison>/`.

Each TCR is present as several codon-optimised variants (`<TCR>.a/.b/.c`). A construct is significant at logFC > 1.5 and FDR ≤ 0.05, and a TCR is called a hit when **at least 2 of its variants** are significant.

`script-volcano-plots-TCL.Rmd` draws the three panels of `results/tcr-library/volcano.pdf`. The TCRs highlighted in the relevant panel are those called in `relevant` minus those called in all three comparisons (`relevant`, `irrelevant` and `positive`), which are enriched regardless of the target; they are listed in `results/tcr-library/relevant_hits_specific.txt`. Variants of a highlighted TCR that do not pass the thresholds are drawn in its colour, semi-transparent. Nothing is highlighted in the irrelevant panel, where no hit is expected.

**rootpath and vhio are processed by two near-identical scripts on purpose.** The differences between `m01-data-load-rootpath.Rmd` and `m01-data-load-vhio.Rmd` (e.g. how library genes are matched, the filters used at doublet removal and rescue, the manual correction of two cells in rootpath) are deliberate, batch-specific choices, not errors.

Order: 1a–1c are independent and can run in parallel; 2 needs 1a, 1b and `tcr_library_annotated.txt` (section 4.1); 3 and 4 need 2; 5 needs 1c and 4. The TCRs were selected from the Cell Ranger contigs of the rootpath samples, not from `m01-rootpath`, which comes later because it needs the library (`tcr_library_clonotypes_pre_post2.rds`, to keep library cells at doublet removal).

**Manual checkpoint after step 2.** The CD8+ non-naïve clusters are named by hand in `m02` (`recode` of `STACAS_snn_res.0.5` into `manual.annotation`). Whenever the integration changes, check the cluster markers printed by `m02` and update that mapping before running steps 3–5; otherwise phenotypes are mislabelled downstream without any error.

If `m02` is re-run, re-run `m04` afterwards: `m02` rewrites `cd8_int_nn.rds` without the iTAG scores that `m04` adds.

AUCs in `m05` are computed per clonotype (a clonotype is reactive if any of its cells is Reactive; score = mean across its cells). A cell counts as Reactive only if it carries both the TRA and the TRB of a reactive TCR reported for its patient. DeLong intervals are unreliable for patients with only 2–3 reactive clonotypes; report the median and range across patients.

## Reproducibility notes

- Seeds are fixed in `setup/setup.R` (`SEED = 123`, `RNGkind("L'Ecuyer-CMRG")`) and in Python (NumPy, `random`).
- BLAS/OpenMP threads are limited to 1. Results should be identical on the same platform; small numerical differences (e.g. UMAP coordinates) are possible on different CPUs.
- `renv.lock` records `future` 1.70.0 with `future.apply` 1.21.0, which declares `future >= 1.80.0`. This is the combination the analyses were run with and it loads correctly; it is kept on purpose.
- The flow-cytometry figures were designed with Arial, which is not installed on Linux. The script falls back to the system sans font, which depends on the machine (e.g. Liberation Sans or Arimo, both metric-compatible with Arial): the drawing is identical, only the embedded font changes.
